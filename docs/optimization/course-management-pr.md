# 课程管理的服务端权限边界

学生能够直接调用课程管理接口创建课程、修改班级课程安排，教师也能直接批量修改课程单元。修复前使用合成账号的真实 HTTP 请求重现了这三种写入，并在数据库确认实际持久化；不是仅凭缺少注解推断漏洞。

本 PR 基于认证响应 PR #5（`57d2a0819db8eb870f22592e2854299368b8e729`），交付课程管理的服务端权限边界。既有主源码工作区保持原样，在独立 worktree 整理并改进原补丁。

## 最终规则与兼容性

- 课程、课程单元、分班安排的 25 个管理入口要求 `admin` 或 `dev`，包含列表、增删改、批量操作及导入导出。使用现有 Shiro 注解和异常响应协议，不新增角色。
- `teachingCourse/queryById` 同时被学习卡片和地图读取。此入口采用资源权限检查，允许管理员，以及课程已分配给本人班级或课程已共享的登录用户。不会因为收紧管理权限而拦住学习页的课程信息读取。
- 新的 `TeachingAccessService` 集中表达这条读取规则，沿用现有课程分班与共享判断。
- 匿名请求返回 HTTP 401；登录后角色不足沿用项目现有 HTTP 200、`success=false`、业务码 510。没有将业务码 510 写成 HTTP 403。

重新只读解析了上游 SQL 的角色菜单关系：`admin/dev` 有课程包与单元管理，`teacher` 在相关教学菜单中只有作业管理，`student` 没有这些管理入口。[来源与摘要](evidence/course-management/source-role-policy.json)。未导入上游账号或业务 INSERT。

## 真实验证

使用全新本地隔离环境，MySQL 13326、Redis 16399、后端 18111，初始化 69 张表和 5 个合成账号。与首页预览的 18101 后端及原 18091 环境分开；全部写入限本次环境。

- 修复前：9/9 项对照检查符合旧行为，包含三种越权写入、持久化证据和清理；这表示问题已重现，不表示旧版本安全。
- 最终候选：**188/188** 项检查通过，结果见 [after.json](evidence/course-management/after.json)。匿名、学生、教师分别检查 26 条路径（25 个管理入口及未授权课程详情），并比较四张业务表的全行摘要及附件字节，确认拒绝请求没有写入或删除。
- 正向检查包括公开课程、学生/教师本班学习入口和详情、共享课程、跨班详情拒绝；分别验证 `admin`、仅有 `dev` 角色时的增删改、批量操作、课程分班及数据库结果。
- 测试中的直接 SQL 角色切换经过实际退出、清除指定合成账号的权限缓存和重新登录；将原管理员临时变为教师后先确认拒绝，再换为仅有 `dev`。这个对照避免将旧管理员权限缓存误判成 `dev` 规则通过，不代表动态角色撤销已通过。
- 导出检查 HTTP 成功和 XLS OLE2 文件头；导入仅检查角色拒绝与空 multipart 的原有校验，**没有验证有效工作簿导入**。导出当前没有 `Content-Type`，因此不能用 MIME 类型作为唯一成功条件；响应头完善另列待办。
- 最终清理恢复课程、单元、分班、文件表和附件原状，恢复管理员角色并删除临时角色，测试会话正常退出。审计日志保留在该隔离环境。

干净 Maven `clean package` 三模块通过。父 POM 跳过 Java 测试，构建成功没有被当成权限验收；权限结果来自上述真实 HTTP/数据库/附件检查。Python 验证脚本语法检查和 Git 差异检查通过。

## 复现

先按 [独立环境说明](../../api/BUILDING.md) 从新目录初始化并启动本候选；只接受已校验归属的本地数据库、Redis、JAR 进程。然后在源码根目录运行：

```sh
python3 api/dev/verify-course-management.py --runtime "$TEACHING_RUNTIME" \
  --output "$TEACHING_RUNTIME/course-management-check.json"
```

基线对照使用同一脚本，传 `--jar` 指向实际运行的 PR #5 JAR，再加 `--expect-legacy`；不要仅换磁盘 JAR 而不重启服务。基线与最终证据各自记录实际 JAR 摘要。[候选摘要](evidence/course-management/candidate.json) 将最终源码、构建产物及检查结果关联。

## 尚未覆盖

完整浏览器角色流程、有效 Excel 导入及导出单元格内容、其他框架管理接口均未据此验收。测试实际发现：隔离配置的 Spring Redis 使用 DB 1，Shiro 权限缓存仍默认 DB 0，实际退出重登没有清除旧角色缓存。这是独立的缓存配置问题，需另行修复；当前只显式清理测试账号缓存来验证各角色边界。单元详情、作业、公开作品及附件的资源访问规则属于后续独立 PR；本 PR 不能代表这些权限已全部修复。未合并、未上线、未连接生产数据库。

本 PR 无数据库迁移。恢复前置 PR #5 的 JAR 会重新暴露本 PR 修复的权限缺口。当前只在隔离环境做候选切换，正式发布仍需组合验收。
