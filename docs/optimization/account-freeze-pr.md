# 账号冻结、解冻与批量状态更新

PR [#55](https://github.com/ZZZZihan/TeachingOpen/pull/55)，基于 [#54](https://github.com/ZZZZihan/TeachingOpen/pull/54)。产品提交 `87cf40225057fb043ec76adc21d140eeae2079f0`。本项已完成下列本地工程验证；真实师生浏览器、人工验收和生产交付各自保留状态。

管理员通过正常冻结接口把用户状态改为 2 后，旧版身份缓存仍可能让原 JWT 继续访问。冻结入口也没有落实页面已有的 `user:status` 权限，逐行更新可造成部分提交，异常后仍可能返回成功。本项围绕一次状态管理操作补齐这些行为。

后端显式检查页面同名权限；操作人来自认证身份，沿用角色等级规则，并落实页面对精确用户名 `admin` 的保护。状态只接受 1/2，逗号分隔的 ID 支持去重、空白和旧页面尾逗号；空批次、缺失目标、越级目标在整批写入前拒绝。事务覆盖全部目标更新，核对影响行数，失败返回明确业务错误并回滚；重复提交相同状态成功且不重复更新。

提交成功后按已有事务感知 Spring Cache 清除用户身份缓存。仅清缓存仍有迟到回填窗口，因此实际 Shiro 认证路径额外通过现有用户查询读取数据库当前状态。冻结后新请求不再信任旧的正常状态缓存；解冻也不再被旧的冻结状态缓存阻断。原有 profile/password 缓存和 JWT 刷新契约保留；仍有效的旧 JWT 在解冻后可以恢复使用。已完成认证并进入执行的请求不追溯撤销。

每次 token 校验增加一次按用户名查询用户的 SQL。这是当前架构下用清晰行为换取一次读取的选择，没有引入缓存版本协议。通知和 Scratch WebSocket 的实际认证也经过此 Realm；未被产品调用的 `TokenUtils.verifyToken` 没有被冒称真实运行路径。

本机观察中，认证路由中位数从旧包 3.546–5.428 ms 变为新包 5.266–8.302 ms，多项 P95 也升高。旧有效测量是第二次完整基准，新测量是第一次，JVM/JIT 预热历史不同；匿名首页同样变慢，且硬件共享。因此这些差值不能归因为新增 SQL，也不能作为性能提升或线上容量验收。每次认证增加一次 SQL 是明确的实现成本；详见 [完整有限对照](evidence/account-freeze-state/benchmark-comparison.json)。
